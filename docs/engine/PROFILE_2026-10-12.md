# Lightweight execution profile — 2026-10-12

Captures started on October 12; analysis and documentation completed October 13.

The best bounded first candidate is shared preparation for an ordinary visible
hires CCK. The renderer performs two pixel-pair operations with repeated mode
selection and setup that survives optimized native code. Active bitplane control
is the second candidate for work shared across display modes. Neither candidate
has been implemented or measured; this record does not predict a gain.

Six full sampled replays, two per workload, reproduce their retained complete
identities with zero measured thread allocations, real PCM and no unsupported
operations. No engine, CPU, runner or workload source changed. This is diagnostic
profiling, not throughput evidence or a passing 1% regression gate. Today's

## Interpretation and limits

This samples managed stacks, not hardware CPU cycles, instructions retired or
cache misses. Inclusive method time overlaps child time and must not be added.
Exclusive leaves include work inlined into the reported method: `TickDevices`
contains video and other device operations, and `ExecuteFrame` includes inlined
synthetic execution. Neither percentage is a measurement of dispatch overhead
alone. The synthetic workloads do not run the native CPU interpreter.

The separately named **interior-tail-v2** analysis selects the engine thread,
validates monotonic/LIFO Speedscope events, and includes intervals with the
`CPU_TIME` marker and `ExecuteFrame` on the stack. It uses half the logged
measured duration, capped at 30 seconds, ending one second before the last sampled
`ExecuteFrame`. An additional one-second start margin is required. This is an
approximate post-warmup boundary; no exact guest-frame markers were inserted.
Window lengths and guest-frame coverage differ between captures.

Background work resumed after the earlier baseline. All 200 telemetry intervals
observe other .NET jobs. Weighted other-package activity, including the trace
collector, is 92–96%; SMT-sibling activity is 97–100%. No telemetry errors occur,
but no formal host-load gate is applied. The long attributed slices below can
skew time-weighted percentages substantially. The count view gives each stack
interval of at least 0.01 ms equal weight; these are interval slices, not
independent hardware samples. Both views are descriptive and have no confidence
bound. Profiled FPS is not reported as throughput.

## Concrete candidates from optimized code

After sampling, three separate bounded JIT replays use the normal warmups and
600 measured fields. Each completes its requested count with zero allocation,
real PCM and no unsupported operations. These shorter replays inspect code;
their output fingerprints are not compared to the full-workload goldens.
`DOTNET_JitDisasm` targets the relevant engine methods with diffable output and
assembly filtering. Tier1/FullOpts sections are retained. Workload-dependent PGO
and inlining produce different shapes; byte/branch counts are not cache-miss or
cycle measurements.

### 1. Share ordinary hires preparation within one physical CCK

[RenderHiresCck](../../CopperMod.Amiga.Lightweight/LightweightVideo.cs#L473)
shifts both playfield pairs, handles blanking/borders, then calls
`RenderHiresVisiblePair` twice for a fully visible CCK. Its comment explicitly
states that no device input occurs between the samples. Each call selects dual
playfield mode, reads sprite placement/output enable, obtains palette/output
storage and invokes the sprite compositor.

The hires Tier1 body is 2,347 bytes, with 72 conditional branches and 12 call
instructions. In generated blocks IG14 and IG21 the same
`test word ptr [rbx+0x124], 0x400` survives twice. IG14–IG15 and IG21–IG22 also
repeat sprite line/last-position/dirty checks and placement loads; palette/output
setup appears in both halves. The native replay independently retains the two
mode tests in IG12 and IG19, with a different inlining shape (1,549 bytes).
`RenderHiresCck` itself accounts for roughly 24–27% of weighted hires leaves.
Only part of that work is potentially removable.

The candidate is a single ordinary-visible four-pixel preparation path: select
mode once and share controls stable within the CCK, with existing boundary and
special-mode fallbacks. Keep both lores sprite positions and both comparator
checks, because a sprite can start at the second position. Observe the required
collisions and advance sprite shifters twice. Keep playfield reload/shift phases,
including border behavior. Sprite state evolves during composition; eliminating
its second preparation checks requires proving the relevant invariants, not
assuming all state is unchanged. Output range checks also remain unless their
safety is established. This is the strongest isolated source/native-code target,
especially for hires; a broad lores or native gain is not established.

### 2. Narrow the active OCS bitplane control path

[Step](../../CopperMod.Amiga.Lightweight/LightweightBitplanes.cs#L180) calls
`AdvanceDdfControl` and then `TryAcceptInput` each active physical CCK. Tier1
`AdvanceDdfControl` is 439 bytes in the synthetic captures and 421 bytes in the
native capture. In the hires body, IG02 and IG05 test `_runActive` twice, IG04
tests `_startPermit`, and the following acceptance helper tests `_runActive`
again. IG08 masks DDFSTOP using the mutable `_ddfMask` field even for the closed
OCS specialization, where the mask is always `0xF8`.

The candidate is to share active-state decisions between control and acceptance,
keep inactive start/release work out of a proven active-run path, and use the
constant OCS mask in generated OCS code. The expected removable work is only a
fraction of total bitplane execution. Raw DDFSTOP is **already cached** through
`LightweightRegisters.DdfStopValue`; caching that register again is not a target.

Any implementation must preserve cancellation on DMA/plane-count changes,
terminal fetch and modulo, same-CCK start/stop behavior, pending output, sync
recovery and mid-line register writes. Prove active/start-permit invariants before
moving tests. Do not forecast grants, skip CCKs or add a scheduler cache.

### Lower priority and already completed work

The immutable output-scale selector remains in the render path, but specializing
it would clone more code. No measured evidence here establishes that tradeoff as
the first target. Constant `wide` arguments are already folded at existing write
sites. Current-slot ownership, shared CPU-grant helpers, address classification,
and device-deadline refresh improvements are already present; this profile does
not resell them as new opportunities. Packed bitplane shifters are also already
implemented.

## Disposition

Actionable candidates are recorded; no optimization, commit or package
publication is included. A future candidate needs affected timing/device tests,
complete workload identity and zero-allocation retention, and the separately
validated idle comparison with the unchanged one-sided 95% upper frame-time
regression bound ≤1%. These loaded diagnostic captures supply no such decision
and do not replace older valid, invalid, accepted or pending evidence.

Raw traces, Speedscope files, logs, telemetry, capture/analysis scripts and native
code remain local under `artifacts/profile-2026-10-12/`; ROMs/media are not
committed. The JSON records hashes and the analysis procedure for audit.
