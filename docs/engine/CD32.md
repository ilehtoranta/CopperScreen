# Experimental Lightweight CD32

CopperScreen can construct a stock PAL or NTSC CD32 with Alice/Lisa, 2 MiB Chip
RAM, a 68EC020 and no floppy drives. The experimental desktop launcher is
available while qualification against WinUAE 6.0.3 continues. The reference revision is
[`857f48fcb09399d4d95527e29a2fdeaedb41f827`](https://github.com/tonioni/WinUAE/commit/857f48fcb09399d4d95527e29a2fdeaedb41f827).
Board clocks and signals come from the
[Commodore CD32 schematic](https://www.amigawiki.org/dnl/schematics/CD32_R3.pdf).

## Running from the desktop

Choose **CD32 (Experimental)…** in the launcher. Select a combined 40.60 ROM or
the separate Kickstart and extended ROMs. Choose the ZIP directly in the
**CD32 disc** picker. If the ZIP contains several CUE sheets or standalone disc
images, choose the disc inside the archive. For Castlevania AGA Fast RAM, select
**PAL** and **8 MiB** Fast RAM.

**Mount CD…** and **Eject CD** change discs during a session. The existing
controller profile's primary and secondary fire controls map to Red and Blue.

## Running the diagnostic profile

```powershell
dotnet run --project CopperMod.Amiga.Lightweight.Runner -c Release -- --cd32 --video-standard ntsc --synthetic-rom-stop --frames 10
dotnet run --project CopperMod.Amiga.Lightweight.Runner -c Release -- --cd32 --rom cd32.rom --extended-rom cd32-ext.rom --cd disc.cue --nvram cd32.nvr --boot-probe artifacts/cd32-replay --frames 600
```

PAL is the default. The ROM loader recognizes the original 40.60 Kickstart and
extended ROM banks using the
[reference ROM identities](https://github.com/tonioni/WinUAE/blob/857f48fcb09399d4d95527e29a2fdeaedb41f827/rommgr.cpp).
Use `--rom` alone for a combined image or for the recognized physical dump.
`--fast-ram-kib 8192` fits an 8 MiB Zorro II Fast RAM board. Fast RAM defaults
to zero for the stock console.
Persistent NVRAM is a raw 1 KiB file. The runner replaces its contents atomically
on exit after a completed guest write.

The disc reader supports Mode 1 ISO and raw BIN/IMG. CUE sheets can reference
multiple files with MODE1/2048, MODE1/2352 and AUDIO tracks, file-relative
INDEX 00/01, and silent PREGAP sectors. WAVE audio uses 44.1 kHz stereo 16-bit
PCM. The CD layout counts complete sectors, matching WinUAE when a WAV track
ends partway through a sector. MP3 audio supports 44.1 and 48 kHz mono or stereo
and is decoded to CD audio sectors on the worker. CD audio plays through the
existing stereo output.
Mount a `.zip` directly when it contains one CUE sheet or one standalone data
image. With multiple discs, select an entry using `archive.zip#/path/to/disc.cue`.
Keep companion tracks in the archive at their CUE-relative paths. The emulator
uses temporary seekable files for the mounted disc and cleans them up on eject,
replacement, or shutdown.
`--cd-turbo` shortens data read delays. The runner's
input script accepts `cdPath` or `ejectCd` for media changes during a boot probe.
Use `cd32ButtonsPort0` or `cd32ButtonsPort1` to attach a pad and send a numeric
mask. Play, Reverse, Forward, Green, Yellow, Blue and Red use bits 0 through 6.
Joystick directions use the existing input fields.

Akiko access widths, packet checksums, ring comparators, prioritization of
data blocks and subchannel buffer layout were implemented against the
[Akiko reference](https://github.com/tonioni/WinUAE/blob/857f48fcb09399d4d95527e29a2fdeaedb41f827/akiko.cpp).
File reads and Mode 1 sector encoding run on a worker. Bus transfers, interrupt
assertion, CD playback position and PCM mix run on the execution owner. Akiko
addresses Chip RAM and guest-configured Zorro II RAM and uses available CCKs
after the existing chipset owners and before CPU grants. The exact drive seek,
DMA arbitration, controller analog timing, CD audio DAC and CIA TOD phases
still require native and hardware evidence.

## Sqrxz boot timing

The 2026-11-24 comparison used the verified Amiga Forever 40.60 ROM pair
and the [developer's Sqrxz ISO](https://www.sqrxz.de/sqrxz/), SHA-256
`F3ECFD7F9D8840EE80F59E8EEE3DEE757E3F6E8498B6CD2C9480A3AFE030C988`.
Stock PAL WinUAE 6.0.3 read the CDTV trademark, read the sectors containing
`S/Startup-Sequence` and reached the Sqrxz v1.2 title screen. Its trace
showed no guest reset during that boot.

At `7670f53`, the ROM sent EEPROM control byte `$A0` and lowered SCL
while releasing SDA with a single long write to `$B80030`. Processing the
direction lane first exposed a transient STOP on the I²C bus. The firmware
missed the acknowledgement, abandoned the nonvolatile-memory access, and
polled the CD before its table of contents was ready. It started the console
animation, recognized `CDTV.TM` later, and called `ColdReboot` at `$E00552`.
Accelerating TOC delivery to 2.2 ms per packet masked that EEPROM failure.

Akiko now presents both EEPROM pin changes in the same strobe. With the stock
TOC cadence, the ROM took the direct boot branch at `$E00558` in PAL field
500 and NTSC field 594. Both read `S/Startup-Sequence` at LBA 343
and rendered the Sqrxz v1.2 title
by field 1,425. The empty-drive PAL control showed the CD32 logo at field
1,100. Instruction timing still differs earlier in the boot. In a PAL
WinUAE run with diagnostic ROM markers, the Kickstart checksum loop ended
in field 22. CopperScreen reached the same instruction in field 33.

## Skeleton Krew

The 2026-11-24 replay used the verified Amiga Forever 40.60 ROM pair and the
[TOSEC CD32 dump](https://archive.org/details/Amiga_CD32_TOSEC_2009_04_18).
The title archive has SHA-256
`43A6AACEC0ADED6D9AEAB5F8DB8E6AFDA929FB411BF795E5352B8BA86596FB6F`.
Mount the extracted CUE with the companion ISO and six WAV files together.
WinUAE 6.0.3 reports the first audio track at LBA 2723 and lead-out at
127891. The previous CopperScreen reader rejected the CUE at MODE1/2048.

The seven-track disc reaches the title menu on both stock console profiles.
Five captured PAL fields each contain a sequence of 120 consecutive stereo
samples from WAV track 2, after accounting for the held samples added by
resampling. The baseline ISO-only replay produces silence at the title.

On PAL, Red at field 1930 entered the single-player menu and Blue at
field 2500 confirmed Joint in the CopperScreen replay. Scripted right and
down inputs moved the player and scrolled the opening Monstrocity area.
Red produced visible shots.

The initial gameplay capture had 128 populated display rows alternating with
128 black rows. The game sets `DDFSTRT=$0010`, before Alice's horizontal
hard start at `$18`. The OCS-style start permit skipped every second row.
The AGA path now retains the early comparison until the hard limit releases.
The corrected field 3300 contains all 256 display rows.

The next comparison found that the left HUD and playfield had different
horizontal alignment. Lisa's `BPLCON1` controls odd and even reloads at 35 ns
granularity. CopperScreen had discarded the fractional part at lower display
resolutions. The shifters now retain each parity's phase through composition.
Lisa's border blank signal also leads the display window by one sample,
which accounts for the former difference at the right edge.

The aligned opening captures from CopperScreen and WinUAE 6.0.3 now match
all 327680 RGB samples at SuperHires horizontal resolution. A PAL replay
through field 4050 exercised right, down, left and up inputs. Captures
every 25 fields show the camera following the player, terrain continuing
across bitplane pointer and fine-scroll changes, and the HUD staying fixed.
WinUAE captures show the same camera response to those directions.

The standalone Sqrxz ISO replay retained its CPU, hardware and output
fingerprints through 1500 PAL fields and matched all six captured frames.

### NTSC intro audio

A stock NTSC WinUAE 6.0.3 replay with the same ROMs and loose CUE recorded
stereo PCM through the built-in AVI recorder. Selecting the active WASAPI
endpoint explicitly resolved the earlier initialization failure. The stock
CPU and drive ran at normal speed, with the WinUAE audio filter and
interpolation disabled. Independent captures reproduced the dropout comparison.
The recorder stored about 1,746 samples per channel per guest field in a
stream labeled 48 kHz. The comparison mapped those samples to the guest
field cadence before aligning the shared waveform.

Both emulators have extended quiet sections in the intro. In the second
audible passage, WinUAE exceeds a PCM magnitude of 15 from reference field
1444 through 1768. With the measured waveform offset of about 297 fields, this
starts about 155 fields (2.6 seconds) before the matching CopperScreen
passage. CopperScreen also drops samples during portions of that passage.
The overlapping waveform correlates above 0.97 in multiple short windows.
CopperScreen's Paula DMA pointers advance through the intro buffer while
the affected sample latches carry zero. The intro uses guest-decoded
Paula audio. The later title and gameplay use CD audio tracks.

During the early gap at CopperScreen field 1853, the guest had loaded
the encoded data and decoded the audio through movie frame 261. Its
movie clock was on frame 253, which contained nonzero audio in the ring.
The decoded data extended to ring offset 17864 and Paula was at offset
20662, in a silent region. In a WinUAE replay that captured guest state
alongside PCM, the player kept 16 decoded audio frames ahead of the movie
clock in this stretch. CopperScreen kept eight ahead. The video frame
counter was also further behind the movie clock in CopperScreen. A later
gap shows disc starvation. At field 2057 the next audio block ended at
byte 2329916, beyond the guest's completed read position of 2326528. The
guest advances past audio blocks that arrive after their playback deadline.

The disc trace has the same 150-sector-per-second cadence within bursts.
The intro file `0intro.lsm` starts at LBA 23. After the read at LBA 433,
WinUAE continues streaming it through LBA 704. CopperScreen reissues
shorter reads, with multi-field gaps between them.
For example, the gap between the emulators' LBA delivery grows from about
314 fields at LBA 433 to 377 at LBA 689. A diagnostic that completes each
Akiko sector transfer immediately still drops the early audio. Turbo
reads and a shorter diagnostic CPU address phase move the boot and the
audio earlier. The aligned dropout persists in both cases. Preserving the
existing sector cadence on adjacent reads also leaves the dropout.
Copper68k 1.5.12 reproduces the same dropout as 1.5.11. The timing
difference that separates the guest's buffer writes from Paula playback
remains open.

A follow-up replay at `3c98591` with Copper68k 1.5.12 produced the same
3,700-field PCM as the earlier stock run. The instruction trace confirmed
that the player had video data buffered while some individual video
decodes took more than two NTSC fields. The decoder did not reach its
usual WinUAE audio lookahead between video blocks.

Two disc-free guest benchmarks isolated the CPU path. With the
instruction cache enabled and display DMA disabled, WinUAE 6.0.3 took
about 4.95 motherboard cycles per NOP/DBRA iteration and 8.2 for the
aligned MOVE/DBRA loop. CopperScreen took 7.09 and 14.1. The guest's
ADPCM inner loop also took about 84 motherboard cycles per decoded sample
in CopperScreen and 42 in WinUAE. The benchmarks used the same operands,
instruction stream and beam-counter measurement on both emulators.

Copper68k's A1200/CD32 profile now uses six native clocks for a cached
taken DBcc and ten on expiry, following the cache-case table in
[Motorola's MC68020 User's Manual](https://www.nxp.com/docs/en/data-sheet/MC68020UM.pdf).
The diagnostic CPU and Chip RAM timing controls moved the copy benchmark
close to WinUAE, but the ADPCM loop still took about 74 motherboard cycles
per sample. They reduced the early dropout while leaving a gap. The
remaining 68EC020 instruction and bus overlap needs qualification.

The cached DBcc correction by itself reduced the NOP/DBRA measurement
from 7.09 to 5.09 motherboard cycles per iteration. A 3,700-field stock
NTSC replay using the local Copper68k development package reproduced
the early gap at about 2.4 seconds after waveform alignment. The shared
CPU test filter passed 63 cases. The separate Lightweight diagnostic
suite passed 1,505 cases with seven optional native tests skipped.

The follow-up timing trace found that indexed ADD, postincrement MOVE
and RTS advanced through a blocking board read and then paid the
cache-case instruction total again. Indexed byte stores and short BSR also
counted transfer time already owned by the posted bus write. The EC020
rounded its native phase at each instruction boundary, even when the board
had advanced only to the rounded view of the same clock. Cached short
branches and overlapped immediate shifts also ran longer than in WinUAE.

[Copper68k f23c05c](https://github.com/ilehtoranta/CopperMod/commit/f23c05c0bed3d25ccba1a3ae01e4600a53b3b63b)
accounts for blocking and posted transfers in those instruction plans,
retains the native half-cycle between board accesses, and applies the
EC020 cache and overlap timings to the affected instructions. The board
still arbitrates and retires each transfer at its existing phase. The
aligned operand probes below ran with the instruction cache enabled and
display DMA disabled. Values are motherboard cycles per operation or
operation group, including amortized loop overhead.

| Probe | Cached DBcc correction | EC020 follow-up | WinUAE 6.0.3 |

| ADD.L indexed | 8.43 | 4.42 | 4.15 |

### Short NTSC gaps and quiet cue

The 2026-11-26 replay at `37cd651` used Copper68k 1.5.14, the same
CUE and ROM pair, and ran for 4,350 fields on stock NTSC. Independent
WinUAE 6.0.3 recordings used point sampling (`sound_interpol=none`) and
area averaging (`sound_interpol=anti`) with the filter off. In the first
quiet cue, the 99.9th percentile of absolute stereo PCM fell from 128/128
to 12/12 with WinUAE averaging. CopperScreen measured 12/6 and comparable
RMS. The cue uses pairs of volume-64 and volume-1 Paula channels. Brief
high/low byte transition pulses account for the large point-sampled
excursions. The remaining small stereo difference needs channel-phase
qualification.

Guest-clock-aligned traces show the decoder processing blocks of 1,324
samples every three video fields into a 64 KiB ring. With AUDxPER at 161,
Paula advanced 441.38 samples per field in the PAL control and 371.58 in
NTSC. The difference in NTSC write and playback rates makes the write
cursor lap playback about every 940 fields. The observed multi-field
gap windows start at movie ticks 651, 1581 and 2527. At those windows the
compressed audio block is within the buffered disc data, while Paula
reaches a cleared ring slot before the decoder writes the replacement.
WinUAE finishes the replacement earlier at the same movie tick.
Turbo reads leave this pattern and worsen the first gap.

The candidate Copper68k package `1.5.15-ec020-overlap.2` uses the shorter
EC020 timings for warm byte and word branch fallthrough, word branches
with a cached target, brief-indexed jumps and byte calls when the
preceding instruction permits overlap. External transfer phases are
retained. The bounds come from sections 8.2.5, 8.2.15 and 8.2.16 of the
[MC68020/EC020 user's manual](https://www.nxp.com/docs/en/data-sheet/MC68020UM.pdf).
The disc-free cached indexed-jump group went from 6.39 to 4.40
motherboard cycles per group, matching WinUAE. The short fallthrough
group went from 3.35 to 2.34, against 2.36 in WinUAE. Aligned and
unaligned copy controls already matched WinUAE within 0.11 cycles per
loop iteration.

With the candidate, the stock NTSC replay removed the multi-field gaps
around movie ticks 651 and 1581. Against the antialiased reference, the
number of fields in multi-field gaps fell from 12 to six and the longest
consecutive gap fell from five fields to two. This counts consecutive
fields with reference PCM above 199 and CopperScreen PCM below 16 after
alignment. Median waveform correlation was 0.994 across 37 matched
windows. Isolated or partial-field differences and brief gaps in the
later passage remain. The candidate is a local development package built from Copper68k
`493470c` on the 1.5.14 source base.
The production solution built cleanly. The candidate passed 3,145 focused
CPU tests and 1,522 Lightweight engine tests, with seven optional native
engine tests skipped.

The 2026-11-26 production Release build used the NuGet.org-signed
[Copper68k 1.5.15](https://www.nuget.org/packages/Copper68k/1.5.15).
The loaded CPU assembly matched the signed package, and the 4,350-field
stock NTSC replay produced PCM identical to the qualified development build.
Against a fresh WinUAE 6.0.3 capture with antialiased interpolation, the
same 1.5.14 baseline had 11 fields in multi-field gaps and 1.5.15 had four.
The longest gap went from four fields to two (about 33 ms). Two two-field
gaps remain at movie ticks 2527–2528 and 2535–2536. Median waveform
correlation was 0.990 across 37 matched windows. The quiet cue's absolute
PCM 99.9th percentile was 12 left and 6 right in CopperScreen, compared
with 12 on both channels in WinUAE.

#### First CD buffer return and late read wakeup

The 2026-11-27 stock NTSC trace aligns the WinUAE CD log with the movie
counter by matching the movie-context marker to the first Lua callback
row. The counters differ by four fields. The first buffer return after
LBA 416 occurs around movie tick 50 in both emulators. The measured
interval from sector completion is about 65 milliseconds in CopperScreen
and 13 milliseconds in WinUAE because CopperScreen completes LBA 416
earlier. WinUAE missed five sector opportunities while refilling its host
cache at LBAs 273 and 358. CopperScreen delivered those sectors on its
regular cadence.

The separate read beginning at LBA 2081 encounters a ROM scheduling delay.
CopperScreen delivers the final Akiko response interrupt while Exec is
switching from the CD task to the movie decoder in supervisor mode.
The handler places the CD task on the ready list. Exec resumes the
interrupted switch and dispatches the CD task at the next vertical blank.
The ROM enables sector DMA about 16.1 milliseconds after acknowledging the
response. WinUAE enables DMA in the same field as the response. The sector
bursts then run at 150 sectors per second.

A 4,350-field Release control based on `af12fe3` used the local
Copper68k `1.5.16-ec020-decode.2` package and the earlier continuous-read
sector-phase change. Comparison against a WinUAE 6.0.3 WASAPI stereo capture
found one silent 48-sample window in each of movie ticks 2532 and 2535,
in both channels. A trial counted the receive comparator's three horizontal
syncs like WinUAE and reduced the LBA 2081 delay to 0.21 milliseconds in
the diagnostic trace.
It cleared the gap at tick 2535 and introduced six silent windows at
tick 2526 and seven at tick 2532 in both channels. A follow-up trial that
reserved the first sector opportunity for seek settling also left gaps at
both target ticks. The timing trials remain experimental.

#### Effect of the earlier Akiko response on the PCM ring

Each diagnostic capture matched its corresponding Release PCM byte for byte
through field 3450. Times below are motherboard time from the start of the
affected field. The WinUAE control used exact sound emulation and matched
the decoder's movie counter at instruction `$22a56`.

| Movie tick and event | CopperScreen control | Scanline-timed receive | WinUAE 6.0.3 |
| --- | ---: | ---: | ---: |
| 2526, first ADPCM decode instruction | 2.72 ms | 3.02 ms | 1.54 ms |
| 2532, first ADPCM decode instruction | 3.09 ms | 7.42 ms | 1.54 ms |
| 2535, first ADPCM decode instruction | 3.70 ms | 2.71 ms | 1.54 ms |

At tick 2526 the receive-timed trial lets the first ROM sector copy interrupt
ADPCM execution at 5.87 ms, before the PCM block is ready. At tick 2532 it
moves two more queued copies ahead of the audio refill and adds a copy during
refill setup. Paula fetches the paired words at `$1b6880` and `$1c6880` at
about 7.44 ms in both CopperScreen builds. The control writes the words at
8.16 ms and the trial at 10.55 ms. The earlier CD wakeup has moved bus and
CPU work into the decoder's deadline. WinUAE starts decoding before its
first copy in that field at about 3.1 ms. At tick 2535 the receive-timed
trial finishes the preceding video decode 2.49 ms earlier and starts the
audio refill 0.99 ms sooner, which clears the measured stereo gap.

Counting horizontal syncs between transmitted command bytes as well as
received responses kept the tick 2535 improvement and left seven silent
one-millisecond windows at tick 2532 in each channel. Transferring two data
words on each eligible cycle produced three entirely silent late fields.
Spreading the block writes over the serial sector interval stalled the
original disc before the intro. The drive connector carries data serially,
and the timing of the intervening Akiko-to-Chip-RAM transfers remains
unverified. The transfer trials are excluded from Release. [CD32 drive
connector measurements](https://github.com/caddy666/Nebula32#how-it-works).

#### Sector backlog before movie tick 2532

Matching the ROM copy entry at `$E59C32` to the CD sector sequence puts
WinUAE's first queued copy, LBA 2083, at tick 2530 line 219. The
scanline-timed CopperScreen trial reaches the same copy at tick 2531
line 67, about 7 milliseconds later. The preceding video decode in
CopperScreen returns late in tick 2530. The ROM wakes the CD task at line
261, and the next vertical blank makes `input.device` runnable at higher
priority. The CD task is preempted at line 23 and resumes at line 57.

WinUAE copies through LBA 2095 in tick 2531. CopperScreen still has LBAs
2093–2095 queued at the start of tick 2532 and copies them before reaching
the audio decoder. LBA 2096 then interrupts the decoder's setup. The
response timing change advances sector availability without advancing
the earlier video return or the start of the bulk copy.

A trial that grants a pending CPU bus request ahead of Akiko sector
DMA cleared the measured one-millisecond windows at ticks 2532 and
2535 in both channels. It used the existing command-relative sector
timing and the local Copper68k `1.5.16-ec020-decode.2` package in a
4,350-field stock NTSC Release replay. The same replay introduced one
silent window per channel at tick 2526. Faster sector transfers and
preserving spindle phase through the short seek also left this earlier
window. The arbitration change remains a candidate.

#### Tick 2526 follow-up

In the initial CPU-priority candidate, the LBA 2081 interrupt hands the CPU
from the ADPCM decoder to the ROM's CD task for about 1.7 milliseconds.
Paula fetches the stereo ring words at `$1b5fe4` and `$1c5fe4` at 8.27 ms
into tick 2526. The guest completes the writes at 9.43 ms, after Paula has
fetched zeros.

The follow-up gives seeks a running integer sector phase and clocks the DMA
comparators on horizontal sync. Transmit DMA advances one byte per scanline
after the comparator hold. The earlier CPU bus arbitration change still
lets a pending CPU request run ahead of the sector transfer. In the
follow-up trace the first sector copy starts at 11.27 ms, after the audio
onset. The paired words finish at 8.70 ms.

Two stock NTSC Release captures with local Copper68k
`1.5.16-ec020-decode.2` produced identical PCM across 4,350 fields.

CPU plan includes that write. The [MC68020 manual, §§8.2.5 and 8.2.16](https://www.nxp.com/docs/en/data-sheet/MC68020UM.pdf#page=252)
gives a five-clock base with one write, plus two clocks for the address
calculation. Crediting the nominal write when the bus already accounts
for it takes the controlled path from 3,658 to 3,654 clocks, leaving 494
against WinUAE. Requiring a cached target produces the same result.

Both stock-hardware JSR trials move the movie start two fields later and
produce identical stereo PCM. After alignment to the fixed WinUAE audio
windows, they play 61 extra active samples per channel at tick 2526 and
miss 100 active samples per channel at tick 2535, with a longest run of
41. Tick 2532 stays clear. The JSR changes remain diagnostic.

The fresh 4,350-field stock NTSC Release run with published Copper68k
1.5.16 reproduces its earlier PCM byte for byte. An independent Release
run using the committed Copper68k source gives the same counts at the
three reference ticks. Both channels show four near-silent samples at
tick 2526 and zero at ticks 2532 and 2535.

#### Displacement AND timing and multiply prefetch before the LBA 2081 copy

At `$F82876` and `$F82938`, `AND.L (d16,An),Dn` waits for an external long
read, then charges its full seven-clock cache case. The
[MC68020 manual, §§8.2.1 and 8.2.8](https://www.nxp.com/docs/en/data-sheet/MC68020UM.pdf#page=227)
includes that read in the seven clocks. Copper68k now measures the
operand wait after fetching the displacement and credits up to three
native clocks. The no-wait test still takes seven clocks. With a
seven-motherboard-clock delay, the instruction takes 18 native clocks
and produces the same result and condition codes.

In the controlled trace, the LBA 2081 copy now starts after 3,650
motherboard clocks over the same 589 instructions. That recovers eight
clocks and leaves 490 against WinUAE's 3,160. The `BCHG`, `BCLR` and
`BSET` write timing trial and the extra register-transfer overlap trial
both leave the copy at 3,658 clocks. Their stock NTSC captures reproduce
the development control's PCM byte for byte.

The final source replay uses the production CopperScreen engine with the
locally built Copper68k fix and runs for 4,350 fields at 48 kHz stereo.
Both channels retain the four near-silent samples at positions 425–428
of WinUAE tick 2526. The tick 2532 and 2535 windows stay clear, and the
longest newly quiet run through tick 2545 is one sample per channel
compared with the earlier development build. The published package used
by CopperScreen is still 1.5.16.

At `$E5A9A8`, the first immediate `MULU.W` finishes its internal plan
before the CPU requests the ROM longword at `$E5A9AC`. Letting the bus
fetch the next instructions during the multiply takes the controlled
path to 3,634 clocks, leaving 474. The stock NTSC replay clears the three
target windows but moves the four-sample miss to reference tick 2529 in
both channels. Combining the prefetch change with the displacement
`AND.L` correction takes the controlled path to 3,626 clocks, leaving
466. Its stock replay still misses the same four samples at tick 2529.
Using the documented 29-clock immediate multiply plan with both changes
leaves four near-silent samples per channel at each of ticks 2526 and
2529.

Allowing ROM prefetch during other instructions' internal cycles as well
takes the controlled path to 3,459 clocks, 299 behind WinUAE. With stock
hardware timing it starts the movie six fields earlier, plays 67 extra
active samples on the left and 66 on the right at tick 2526, and misses
92 active samples in each channel at tick 2535. It also misses four
samples per channel at tick 2529. The shorter timing in the controlled
trace comes with audio regressions in the stock replay.

#### Successor fetch ordering in the 490-clock trace

The instrumented replay matches all 589 instruction addresses and
reproduces the 3,650-clock copy entry. Of the 490-clock difference,
164 clocks accrue in the handler, 64 during the task switch and 262 in
the worker. The bus log shows 1,110 clocks in 369 ROM fetches and 714
clocks in 139 Chip RAM long reads.

In the [MC68020 instruction pipe](https://www.nxp.com/docs/en/data-sheet/MC68020UM.pdf#page=28),
the sequencer can advance while the bus supplies an aligned instruction
longword. The `$F8288A` store prefetches `$F82890` and `$F82894` before
posting its byte write. The consuming `LEA` can use the first fetch
before the second fetch and write finish. Using the ready time of each
fetched word instead of waiting for the latest bus completion changes
15 such waits in the trace. It changes intermediate phases and still
reaches the copy at 3,650 clocks.

Allowing one successor longword to fetch during an immediate word
multiply recovers 14 clocks in the controlled trace. The Release replay
clears the four missing samples at tick 2526 and plays four samples
early per channel in that window. Tick 2529 stays clear. Fetching the
successor during the completion of postincrement `MOVEM.L` loads
recovers 12 clocks in the controlled trace. That trial plays 61 extra
active samples in each channel at tick 2526 and misses 100 active
samples per channel at tick 2535. Allowing the single-longword prefetch
during other ROM instructions reduces the diagnostic delay to 352
clocks and introduces four low samples per channel at tick 2529.

Restricting the immediate-multiply prefetch to ROM produces the same
stereo capture as allowing it for all cacheable code. Restricting it to
RAM reproduces the committed development capture byte for byte. Requiring
an idle bus at the multiply's prefetch request preserves the 14-clock
gain and the four early samples at tick 2526. In the copy trace,
limiting `MOVE` successor prefetch to one pending external
transfer leaves 490 clocks. Combining that limit with multiply prefetch
leaves 478 clocks and still plays four samples early per channel at
tick 2526.

The displacement word `AND` and `OR` read credits, the postincrement
longword read/write credits, and the displacement register-store
credits each leave the controlled copy entry at 3,650 clocks. Their
stock-hardware replays retain the same sample counts in all four
reference windows.

The fresh stock NTSC Release replay using published Copper68k 1.5.16
reproduces its previous 4,350-field stereo PCM capture byte for byte.
The fixed WinUAE windows show four near-silent samples per channel at
tick 2526 and none at ticks 2529, 2532 and 2535.

## Castlevania AGA

The 2026-11-24 replay used the [developer's Fast RAM CD32 release](https://www.mediafire.com/file/osemoc30rnxt0v0/CastlevaniaAGA_CD32_ISO_FASTRAM.zip/file)
with SHA-256 `AA705B73858F12220D2B5F3BAD253D4804B51492257C7E2A3495FE7BE519C3C6`.
Mount the ZIP directly. For a loose mount, keep the supplied CUE beside the ISO
and all 13 MP3 tracks. The PAL profile used 2 MiB Chip RAM, 8 MiB Zorro II Fast
RAM at `$200000`, the verified Amiga Forever 40.60 ROM pair and normal drive
speed.

With Fast RAM fitted, the ROM placed Akiko's command and response rings at
`$9FFC00` and the sector buffer at `$210000`. Masking these addresses to Chip
RAM corrupted the command packets and prevented the ROM from reading sectors.
Akiko now accesses the configured RAM bank at those addresses.

CopperScreen and WinUAE 6.0.3 reached the title and selected CD audio track 7.
CopperScreen placed that track at LBA 75356 using the MP3s' decoded durations
at their source rates. WinUAE reported LBA 81972. In CopperScreen, the captured
field 1725 contained 883 consecutive stereo samples from the 48 kHz source
after CD DAC resampling and duplicate output samples were accounted for.

With a CD32 pad on Port 2, Blue at field 1905 started the game. Stage 01 was
visible by field 2300. Scripted directions, Red and Blue exercised movement,
the whip and jumping. Track 11 played during the opening area. The replay
ended in Stage 01 at field 3250.

Mounting the original ZIP reproduced the loose CUE replay's video and PCM

The runner removed its temporary disc files on exit.
The Windows desktop picker also opened the original ZIP with this profile.
The desktop reached the title and opening story, then ejected and remounted
the archive from the CD32 controls.

WinUAE 6.0.3 also mounted the original ZIP directly for the title comparison.
In the title's 16-bit fetch mode, `BPLCON1=$22FF` places both reload matches
just after the next fetch boundary. CopperScreen transferred the new
`BPL1DAT` group to Lisa's intermediate latch too early. A match therefore
selected the following word, shifting the playfield left by 16 low-resolution
pixels and showing surplus data at the right edge. The intermediate latch
now changes at the reload phase so a preceding match can still use its own
word. The title and credits align with the WinUAE capture, and the yellow
stripes at the right are gone. The same ZIP replay reached Stage 01 at field
2400 with CD audio active. The four scroll cases in
