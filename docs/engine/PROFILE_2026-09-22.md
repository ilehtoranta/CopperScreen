## Steady execution attribution

Select the thread containing `ExecuteFrame`, then a fixed eight-second interval
ending two seconds before its last sampled engine execution. Measured execution
lasted approximately 19.88 / 22.41 / 14.65 seconds, respectively, so each interval
fits within post-warmup execution with margin. This is an interior tail sample,
not the entire measured frame interval. Startup and shutdown are excluded.

Speedscope interval duration supplies the weight. The `CPU_TIME` sample marker
is attributed to its immediate code caller. Percentages below are disjoint

Zero sampled exclusive attribution does not mean a device was disabled or did
no work: inlining, the synthetic CPU workload and finite sampling matter.
For example, native `GrantCpuWord` alone accounts for 4.00% under Other.

Native CPU costs include `ExecuteSingleInstruction` 8.98%,
`ExecuteInstructionBody` 7.98%, `TryExecutePlannedKind` 7.26% and

the device work their calls eventually perform.

Whole-trace reports, which include boot/warmup, independently show the same
broad priorities. Their percentages differ and are retained separately, rather
than substituted for the steady-window results. Each workload was profiled once;
these estimates rank investigation targets, not small statistically established
differences or predicted speedups.

## Recommended optimization order

1. Inspect generated code within `TickDevices` and its inlined rendering first.
   Separate repeated rendering/control checks from actual output work before
   choosing a small change. Its sampled attribution does not justify removing
   device checks or skipping CCKs wholesale.
2. Simplify the measured bitplane fetch/control path, preserving input/output
   phases, pending completions, terminal fetches and mid-line register effects.
   Hires composition is an additional substantial, separately visible target.
3. Investigate native CPU host-loop/bus-access overhead, then Copper68k dispatch
   as a separate CPU change if needed. Preserve prefetch, exception, interrupt
   and bus timing. CPU package changes require their own pin and validation.

A further 5% gain remains a target, not a result. Any candidate needs unchanged
complete-workload fingerprints, focused and affected native correctness checks,
zero steady-state allocations and the unchanged six-pair comparison against the
accepted baseline. The default one-sided 95% upper frame-time regression bound
remains at most 1% for every retained workload; earlier exceptions do not transfer.
