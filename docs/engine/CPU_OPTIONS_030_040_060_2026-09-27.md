# Experimental 030/040 integration and 060 diagnostic core — 2026-09-27

Follow-up: the [040 Lotus investigation](LOTUS_III_040_INVESTIGATION_2026-09-27.md)
localizes the original prompt stall to missed input edges. A separately named
two-field input variant reaches a driving demo on unchanged binaries. The
original results below and their manifest remain retained.

CopperScreen now offers **68030 and 68040 as experimental OCS accelerators**.
Both boot the supplied native Kickstart 1.3 hard-disk workload, allocate true
Fast RAM and persist the independently checked OFS proof file. The 030 reaches
Lotus III menus; the 040 remains at its disk-two prompt under the retained input
script. That is an open compatibility issue, not a successful gameplay replay.

A distinct **68060 integer-focused diagnostic core** is available through the
engine and runner. It is unavailable in the desktop: Kickstart 1.3 constructs
a four-byte initial NULL FPU task frame, while a 060 restores twelve bytes.
The resulting context corruption is reproduced below. Enabling the choice
requires 060-aware OS/task support and further CPU conformance work.

The machine remains PAL OCS with its existing 16-bit motherboard bus and
512 KiB Chip + 512 KiB slow RAM. Optional Zorro II Fast RAM is unchanged.
This does not establish A1200/AGA, full MMU/FPU, physical accelerator timing,
040 JIT or general game compatibility.

## CPU and host changes

The [CopperMod owner commit](https://github.com/ilehtoranta/CopperMod/commit/ef205a863facc471a5852cee893bcb4508e77d94)
corrects the 040 CACR instruction/data enable bits to 15/31. Independent
self-modifying-code cases reproduce three failures against `.54`; two controls
pass. CINV/CPUSH implements instruction/data selection, line/page/all scope,
privilege checks and invalid-encoding exceptions. The 060 data-push inhibit bit
is respected. Chip RAM now permits instruction caching on 030/040.

Cache organization remains a bounded implementation: physical capacities,
associativity, cache-fill timing and copyback behavior are not certified. Data
writes remain write-through. Correct register encodings must not be weakened
to imitate an older CPU when investigating software compatibility.

The new 060 model has its own PCR identity, single supervisor stack, software
M bit, removed-register exceptions, vector-61 removed-integer traps, aligned
CAS boundary and exception return handling. It implements FPU control-register
transfers and architectural twelve-byte NULL/IDLE save/restore frames.
FPU arithmetic, exceptional FPU frames, enabled MMU/transparent translation,
BUSCR operation, full indexed forms and full exception/trace conformance remain
unavailable or incomplete; unsupported implemented boundaries stop explicitly.
It does not alias the 040 execution core or use 040/68881 task-frame layouts.

The desktop persists and selects 030/040 profiles, labels them experimental,
and explains the unavailable 060 choice. Runner `--cpu 68030`, `68040` and
`68060` select the corresponding models. Diagnostic metadata records the
declared native-to-motherboard clock ratios: 2 for 020/030, 4 for 040 and 8 for
060. The 040/060 instruction timing is approximate fixed timing; the bridge
still resolves motherboard bus accesses through the existing scheduler.

## Exact 060 native blocker

A bounded, external instruction trace using the final `.55` candidate records:

1. At `$FC10F0`, `FSAVE -(A5)` changes A5 from `$C014BE` to `$C014B2` and writes
   the twelve-byte NULL frame specified for a 060.
2. At `$FC114C`, `FRESTORE (A5)+` receives A5 `$C0372C`, whose first bytes are
   `00000000 00FE5E30 00000000`. The OS supplied only the first four bytes as its
   initial NULL frame; saved task context follows it.
3. The architectural restore advances A5 twelve bytes to `$C03738`. Subsequent
   OS register restoration is shifted and resumes the task at PC `$00000000`.
4. Execution at address four raises an illegal-instruction exception. The later
   unsupported `$0497` at `$FC088C` is inside that exception handler; implementing
   it would not repair the initiating context corruption.

The trace is `060-context-trace-final.log`; its hash and probe-source hash are
in the manifest. No tracing was added to the production hot path. The desktop
must keep 060 unavailable until a compatible OS/task implementation is selected
and validated. Replacing twelve-byte frames with old four-byte frames would
misrepresent the CPU and is not a valid fix.

## Package and reproduction boundary

The consumer currently pins **local, unpublished `Copper68k 1.4.2-ocs020.55`**
from the owner commit above. The package was packed once with package validation;
README, icon, XML API documentation, model entry and repository metadata were
checked. Its DLL matches the runner, exact-package CPU test fixture and 060
trace probe. All eight consumer/probe lockfiles resolve this candidate.

A clean checkout needs that exact local package until an explicitly authorized
release. The preceding [`.54` release](COPPERHDF_020_2026-09-27.md#authorized-public-release)
is already public and verified. Its approval does not authorize `.55` publication.
No ROMs, OS files, game media or local binary artifacts are committed.

Architectural expectations come from [MC68040UM, section 2.2.2.5](https://www.nxp.com/docs/en/reference-manual/MC68040UM.pdf),
[M68000PRM, CINV/CPUSH](https://www.nxp.com/docs/en/reference-manual/M68000PRM.pdf),
and [MC68060UM, sections 3.2.2, 8.2.4, 11.1.2, C.2 and appendix D](https://www.nxp.com/docs/en/data-sheet/MC68060UM.pdf).
The 060 manual specifies twelve-byte state frames, including NULL; the observed
Kickstart task-frame incompatibility follows from that contract and the trace.
